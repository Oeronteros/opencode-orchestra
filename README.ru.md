[English](README.md) · **Русский** · [简体中文](README.zh-CN.md)

OpenCode Orchestra превращает сложный запрос в контролируемый multi-agent workflow. Плагин классифицирует задачу, выбирает подключённые модели, запускает узких специалистов, объединяет их доказательства, применяет изменения, проверяет результат и ведёт локальный учёт стоимости и использования.

**OpenCode Orchestra предназначен для OpenCode v2** и загружается через API плагинов `setup`. Для OpenCode 1.18.29 и новее также сохранён модуль совместимости.

- Один основной агент и команда специалистов с ограниченными правами
- Автоматическое обнаружение моделей, бюджетные режимы, overrides и fallback-цепочки
- Dependency-aware выполнение с жёсткими лимитами параллелизма, глубины и владения
- Опциональные изолированные Git worktrees для параллельных редакторов
- Управляемый Chrome с постоянными профилями, Playwright для UI и DevTools для диагностики
- Локальная панель с live-активностью, токенами, стоимостью, моделями, агентами и состоянием MCP
- Диагностика, MCP smoke-тесты, ограниченные автономные циклы и офлайн-голосовой ввод

## Быстрый старт

Требования: [OpenCode v2](https://opencode.ai/), Bun 1.2 или новее, Node.js 22.12 или новее и поддерживаемый провайдер моделей OpenCode. Для управляемого браузера дополнительно нужны OpenCode 2.0.16 или новее и отдельно установленный Chrome.

```bash
bunx @oeronteros-1/opencode-orchestra@latest install
```

Перезапустите OpenCode и выполните:

```text
/orchestra Найди причину периодического сбоя авторизации, исправь её и запусти нужные тесты
```

Команды состояния:

```text
/orchestra-status
/plugin-status
/orchestra-resume
```

Установщик идемпотентен. Перед изменением конфигурации OpenCode он создаёт резервную копию и сохраняет существующие плагины и MCP-записи. `--force` заменяет записи сопутствующих MCP, которыми управляет установщик; существующие браузерные MCP и `orchestra.jsonc` сохраняются. В новой конфигурации браузер включён через `browser.mode: "auto"`; в существующей без секции браузера он остаётся выключенным.

### Поддержка и переход на OpenCode v2

В OpenCode v2 плагин загружается через API `setup`. Установщик заранее добавляет имена агентов Orchestra в конфигурацию, поскольку плагины v2 могут изменять существующих агентов, но не создавать их через `agent.transform`. После перехода с OpenCode 1.x повторно запустите `install`. Для OpenCode 1.18.29 и новее сохранён прежний входной модуль совместимости. OpenCode v2 преобразует поддерживаемые поля конфигурации v1 при загрузке, поэтому переписывать конфигурацию необязательно. См. [официальное руководство](https://opencode.ai/v2/docs/build/plugins/migrate-v1).

## Как это работает

```text
запрос
  → классификация задачи и анализ возможностей
  → запечатанный dependency-aware план с TaskContract
  → параллельные evidence-workers в рамках общих лимитов
  → однократное объединение с сохранением источников
  → опциональный judge для критического риска или неразрешённого спора
  → реализация, интеграция и общая проверка
  → локальная телеметрия и учёт стоимости
```

В режиме `ebobo` задачи профиля research используют ограниченный исследовательский рой. При стандартном лимите в восемь узлов четыре worker-а независимо исследуют разные гипотезы, два worker-а второго раунда получают все результаты первого раунда и направляют усилия на наиболее перспективные уцелевшие подходы, `orch-merge` объединяет общий журнал гипотез, а `orch-judge` независимо проверяет итог. Математические доказательства, гипотезы, научные задачи, неудачные подходы, контрпримеры и повторно используемые промежуточные результаты передаются между раундами с указанием происхождения. Предварительный или неопределённый вердикт judge не считается завершением.

`orch-lead` — публичный основной агент. Он может редактировать текущий workspace, запускать проверки и координировать команду. Внутренние workers по умолчанию скрыты из обычного выбора агентов и имеют более узкие разрешения.

| Агент | Роль | Запись файлов |
|---|---|---:|
| `orch-lead` | Планирование, координация, реализация и итоговая проверка | Да |
| `orch-repo` | Структура репозитория, история Git, зависимости и blast radius | Нет |
| `orch-docs` | Официальная документация и upstream-исходники | Нет |
| `orch-tests` | Воспроизведение, покрытие и команды проверки | Нет |
| `orch-research` | Стандарты, реализации и исследование экосистемы | Нет |
| `orch-critic` | Независимая критика и проверка предположений | Нет |
| `orch-security` | Границы доверия, авторизация, секреты и данные | Нет |
| `orch-visual-reference` | UI-референсы, взаимодействия и motion | Нет |
| `orch-visual-generate` | Исследовательская генерация визуалов | Только созданные assets |
| `orch-visual-review` | Проверка скриншотов, иерархии, доступности и регрессий | Нет |
| `orch-editor` | Изолированная реализация в назначенном worktree | Только назначенная область |
| `orch-integrator` | Детерминированная fail-closed интеграция проверенных коммитов | Только Git-интеграция |
| `orch-merge` | Синтез доказательств с источниками и неопределённостью | Нет |
| `orch-judge` | Арбитраж критического риска или неразрешённого спора | Нет |

### Ограничители выполнения

- `parallelWorkers` задаёт общий жёсткий лимит одновременных workers во всём дереве.
- `maxWorkers` ограничивает число уникальных worker-узлов во всём дереве задачи.
- `maxDelegationDepth` ограничивает глубину вложенной делегации.
- Каждый узел получает запечатанный TaskContract: цель, входы, критерии готовности, разрешённые пути, эксклюзивные ресурсы и бюджет делегирования.
- Независимые узлы, претендующие на один изменяемый ресурс, выполняются последовательно.
- Сбой зависимости блокирует downstream-узлы и не позволяет частичному выполнению незаметно продолжиться.

По умолчанию разрешено восемь workers, восемь параллельных workers и глубина делегации два. Эти лимиты проверяются runtime, а не только промптами.

### Возобновление после перезапуска

Orchestra локально сохраняет запечатанный план, состояния узлов, результаты зависимостей и проверенные Git-коммиты в `.orchestra/orchestration/runs.json`. После перезапуска активные и ожидающие узлы работы с репозиторием становятся незавершёнными; уже завершённые узлы не выполняются заново. Прерванные браузерные узлы блокируются и требуют проверки состояния сайта перед явным повторным запуском, чтобы внешние изменения не повторялись автоматически.

```text
/orchestra-resume
/orchestra-resume <исходный-session-id>
```

Без аргумента продолжается последний незавершённый запуск. Сохранение можно отключить или перенести:

```jsonc
{
  "orchestration": {
    "persistence": {
      "enabled": true,
      "directory": ".orchestra/orchestration"
    }
  }
}
```

Файл состояния локальный, но содержит результаты workers; если они могут включать чувствительные данные, каталог следует защищать так же, как рабочий репозиторий.

### Подтверждённое завершение

Перед итоговыми проверками `orch-lead` регистрирует точные команды и ожидаемые артефакты через `orchestration_set_verification`. Команды выполняются обычным инструментом `bash`, поэтому к ним применяются разрешения OpenCode. Runtime отмечает gate успешным только после успешного завершения соответствующего вызова; наличие артефактов он проверяет непосредственно в workspace.

`orchestration_complete` различает четыре состояния: работа продолжается, агент заявил о завершении, проверка провалена и завершение подтверждено. По умолчанию запуск нельзя отметить подтверждённым без хотя бы одного gate и без успешного завершения всех узлов плана. Требование можно отключить через `orchestration.verification.required`, а число gate ограничивается `orchestration.verification.maxGates`.

### Бюджет задачи

Помимо режима выбора моделей можно задать жёсткие лимиты стоимости, токенов и времени. Значение `0` отключает соответствующий лимит:

```jsonc
{
  "orchestration": {
    "taskBudget": {
      "maxCostUSD": 2,
      "maxTokens": 120000,
      "maxMinutes": 15,
      "unknownPricing": "warn"
    }
  }
}
```

До запуска Orchestra оценивает и резервирует бюджет всего DAG. План, оценка которого уже превышает лимит, не запускается. Между worker-вызовами runtime сверяет фактическую стоимость и токены из локального ledger; время считается от начала запуска и сохраняется при перезапуске. `unknownPricing: "block"` запрещает запуск или продолжение, если цену нельзя определить; `"warn"` явно исключает такие вызовы из USD-суммы. Эти же лимиты можно передать одному вызову `orchestra_route` через `maxCostUSD`, `maxTokens` и `maxMinutes`.

### Граф выполнения и адаптивная команда

Режим `ebobo` сохраняет полную ограниченную команду для максимального качества; минимальная стартовая команда применяется в остальных режимах.

Страница **Runs** в dashboard показывает сохранённый граф зависимостей, контракты узлов, результаты, ошибки, gate завершения и бюджет. Активную ветку можно отменить, а проваленную, заблокированную или отменённую — перезапустить. Повторный запуск сбрасывает downstream-результаты; запоздавший ответ старой попытки не может перезаписать новую.

Пока узел ожидает запуска или работает, lead может передать ему ограниченное уточнение через `orchestration_relay_context`. Уточнение сохраняется при перезапуске процесса и повторе ветки, а активный dispatch запрашивает у той же worker-сессии полный исправленный результат до отметки об успехе.

По умолчанию Orchestra начинает с двух специалистов и синтеза, сохраняя остальные слоты. `orchestration_adapt` создаёт новую версию плана только по наблюдаемому сигналу: неудачной репродукции, противоречию, границе авторизации, пробелу в документации, performance- или visual-регрессии, низкой уверенности либо подтверждённому отсутствию прогресса. Для сигнала нужны конкретные свидетельства; повторные сигналы игнорируются. Настройки: `orchestration.adaptive.initialWorkers`, `maxExtensions`, `minEvidenceItems`.

Прогресс bounded loop определяется успешными узлами, проверенными коммитами и пройденными gate. Перефразирование строки `MORE` больше не сбрасывает лимит отсутствия прогресса.

### Встроенные eval

`opencode-orchestra eval --json` выдаёт версионированный набор из пяти сценариев и структурное покрытие маршрутизации для solo, eco, balanced, quality и ebobo. `--results results.json` добавляет реальные метрики успешности, времени, USD-стоимости и токенов. `--write baseline.json` сохраняет baseline; `--baseline baseline.json` завершает команду с кодом 2, если успешность упала более чем на пять процентных пунктов либо среднее время/стоимость выросли более чем на 20%.

### Повторно используемые проверенные знания

После подтверждённого `orchestration_complete` инструмент `orchestra_knowledge_record` сохраняет решение, точную тестовую команду или ограничение вместе со свидетельствами, запуском-источником, версией плана, Git revision и затронутыми путями. `orchestra_route` и `orchestra_knowledge_query` используют только актуальные записи. Запись устаревает после TTL, при незакоммиченных изменениях её путей или если пути изменились после исходного revision. По умолчанию локальная база находится в `.orchestra/knowledge/verified.json` и ограничена `orchestration.knowledge.maxEntries`.

## Установка

Стандартный установщик настраивает Orchestra и пытается подготовить связанные инструменты:

- навыки [Superpowers](https://github.com/obra/superpowers);
- [Context7](https://github.com/upstash/context7) для актуальной документации библиотек;
- [Codebase Memory](https://github.com/DeusData/codebase-memory-mcp) для индексации репозитория и impact analysis;
- [MemoryGraph](https://github.com/memory-graph/memory-graph) для долговременных решений и повторно используемых знаний;
- официальный Git MCP, ограниченный активным репозиторием;
- [GitHub MCP](https://github.com/github/github-mcp-server) для удалённых репозиториев, issues и PR;
- ast-grep MCP для структурного поиска;
- пакеты Playwright MCP и Chrome DevTools MCP с фиксированными версиями для управляемого браузера;
- локальный voice overlay и модель Whisper на поддерживаемых платформах.

Ошибка установки опциональной зависимости не мешает настроить основной плагин. При неудачной подготовке Codebase Memory или MemoryGraph нерабочая команда не записывается. Git и ast-grep могут быть настроены после неудачного прогрева: `uvx` повторит попытку при запуске. Браузерные MCP входят в зависимости пакета и регистрируются по мере необходимости в OpenCode v2; сам Chrome установщик не скачивает.

Для однократного подключения GitHub MCP установите [GitHub CLI](https://cli.github.com/) и введите команду **внутри OpenCode**:

```text
/github-connect
```

Команда откроет вход через браузер, если GitHub CLI ещё не авторизован, сохранит токен в `~/.config/opencode-orchestra/github-token` и настроит OpenCode на чтение этого файла. Токен хранится в файле открытым текстом; на Unix файл доступен только владельцу. После этого перезапустите OpenCode. Вместо команды можно задать `GITHUB_PERSONAL_ACCESS_TOKEN` в окружении OpenCode. Токену нужны права на репозитории и действия, которые вы собираетесь использовать.

Основные параметры установки:

```text
--no-context7
--no-github
--no-codebase-memory
--no-memorygraph
--no-git
--no-ast-grep
--no-playwright
--browser-mode MODE
--no-superpowers
--no-voice
--no-deps
--dry-run
--force
--config-dir DIR
```

Просмотр изменений без записи файлов и загрузки зависимостей:

```bash
bunx @oeronteros-1/opencode-orchestra@latest install --dry-run
```

`--browser-mode` принимает `off`, `auto`, `playwright` или `devtools` и действует только при создании новой конфигурации Orchestra. `--no-playwright` задаёт `off`; сочетание с `--browser-mode devtools` оставляет только DevTools. Сочетание с `auto` или `playwright` считается ошибкой. `--no-deps` пропускает подготовку сопутствующих инструментов, но браузерные MCP остаются зависимостями npm-пакета.

## Управляемый браузер

Orchestra использует собственные профили Chrome без браузерного расширения. В режиме `auto` навигация и формы преимущественно работают через Playwright, а глубокая диагностика и производительность — через Chrome DevTools. Оба инструмента подключаются к одному управляемому браузеру. Для поиска документации по-прежнему используются web search, webfetch и Context7.

В существующей установке добавьте в глобальный или проектный `orchestra.jsonc`:

```jsonc
{
  "browser": {
    "mode": "auto",
    "profile": "default",
    "profiles": ["default", "work-account"],
    "sharedProfiles": [],
    "headless": false
  }
}
```

После изменения конфигурации перезапустите OpenCode. Команды выполняются из каталога проекта:

```bash
bunx @oeronteros-1/opencode-orchestra@latest browser status --directory .
bunx @oeronteros-1/opencode-orchestra@latest browser login --directory . --profile default
bunx @oeronteros-1/opencode-orchestra@latest browser profiles --directory .
bunx @oeronteros-1/opencode-orchestra@latest browser select --directory . --profile work-account
```

Войдите на сайт непосредственно в окне Chrome, открытом командой `browser login`, затем закройте Chrome или нажмите Ctrl+C перед использованием этого профиля в OpenCode. Cookies и localStorage сохраняются после перезапуска браузера, но сайт может завершить авторизацию. Профили привязаны к репозиторию; его Git worktrees используют ту же идентичность. Имена аккаунтов должны быть перечислены в `browser.profiles`; общий профиль между проектами требует явной записи в `sharedProfiles`. `browser select` записывает проектное переопределение, которое вступает в силу после перезапуска OpenCode.

Браузерные сценарии выполняются последовательно и требуют одну вкладку страницы. Контракты задач ограничивают origins и операции; разрешения OpenCode продолжают действовать. Существующие пользовательские браузерные MCP блокируют создание дублирующих управляемых серверов. Browser Code Mode отключён. Отсутствие Chrome или занятый профиль вызывает ошибку браузерного сценария, при этом оркестрация работы с репозиторием остаётся доступной.

Задайте абсолютный путь к Chrome через `browser.executable`, а к настоящему Node — через `browser.nodeExecutable`, если OpenCode работает под Bun. Хранение профилей, права, переключение инструментов, артефакты и диагностика описаны в [docs/browser.md](docs/browser.md).

## Маршрутизация моделей

Стратегия `auto` получает модели подключённых провайдеров OpenCode и определяет их полезные возможности: tools, reasoning, vision, image output и размер контекста. Автоподбор заполняет только пустые пулы и не заменяет непустой ручной пул.

Если каталог моделей временно недоступен, Orchestra не задаёт модель агенту, сохраняя текущий выбор пользователя в OpenCode.

### Бюджетные режимы

| Режим | Политика |
|---|---|
| `eco` | Предпочитать бесплатные модели и ограничивать premium escalation |
| `balanced` | Предпочитать subscription/free с ограниченной premium escalation |
| `quality` | Предпочитать сильные lead-модели и разрешать платных кандидатов |
| `ebobo` | Для исследовательских задач включать ограниченный рой, предпочитать frontier arbitration и всегда обращаться к judge |

Бюджет влияет на модели, лимит платных вызовов и эскалацию, но не увеличивает runtime-лимиты агентов.

### Модели отдельных агентов и fallback

```jsonc
{
  "$schema": "https://unpkg.com/@oeronteros-1/opencode-orchestra@latest/schema/opencode-orchestra.schema.json",
  "budget": "balanced",
  "models": {
    "strategy": "auto",
    "agents": {
      "orch-lead": "provider/primary-model",
      "orch-repo": "provider/code-model",
      "orch-judge": "provider/frontier-model"
    },
    "fallback": {
      "enabled": true,
      "maxRetries": 2,
      "agents": {
        "orch-repo": ["provider/backup-one", "provider/backup-two"]
      }
    }
  }
}
```

Точное переопределение в `models.agents` имеет наивысший приоритет. При rate limit, timeout и provider 5xx Orchestra может перейти к следующей совместимой модели. Ошибки аутентификации, разрешений и невалидного запроса останавливают цепочку.

Runtime-fallback и учёт жизненного цикла выполняются напрямую для всех subagent Orchestra. При запуске editor создаётся изолированный Git worktree от зафиксированной базовой ревизии; integrator работает в основном checkout только после проверки каждого editor commit. Только primary lead остаётся на нативном пути OpenCode.

## Параллельное редактирование

Параллельные редакторы экспериментальны и по умолчанию выключены:

```jsonc
{
  "orchestration": {
    "parallelEditors": 3,
    "worktreeRoot": ".orchestra/worktrees"
  }
}
```

Каждый editor получает непересекающееся владение путями и отдельный Git worktree. Перед интеграцией Orchestra проверяет фактический diff коммита, ancestry и границы ownership. Integrator строит детерминированную карту конфликтов и интегрирует либо все проверенные коммиты, либо ни одного.

При нарушении ownership, ошибке ancestry или Git-конфликте интеграция останавливается, а worktrees сохраняются для диагностики. После успешной интеграции lead всё равно обязан выполнить общую проверку.

## Bounded Loop

Bounded Loop позволяет `orch-lead` продолжать одну цель в нескольких контролируемых итерациях. Функция включается явно:

```jsonc
{
  "orchestration": {
    "loop": {
      "enabled": true,
      "maxIterations": 10,
      "maxMinutes": 30,
      "noProgressLimit": 3
    }
  }
}
```

```text
/loop Исправь падающие тесты
/loop --file docs/plan.md
/loop status
/loop stop
```

Следующую итерацию разрешает только незаключённая в цитату последняя строка `MORE: <оставшаяся работа>`. При включённой обязательной проверке `DONE: <итог>` завершает цикл только после успешного `orchestration_complete`; иначе цикл получает состояние `unverified`. Запрос разрешения и неизвестный ответ приостанавливают цикл; ошибка и новое сообщение пользователя останавливают его.

Состояние самого bounded loop хранится в памяти и теряется после перезапуска OpenCode. Непустой `verifyCommand` по-прежнему работает fail-closed; безопасная проверка выполняется через зарегистрированные gate и обычные permissioned-инструменты OpenCode.

## Голосовой ввод

Стандартный установщик ставит локальные ffmpeg и Whisper для Linux x64 и Windows x64 и загружает модель `ggml-base.bin`. Аудио не отправляется во внешний сервис распознавания.

Во всех режимах доступны русский, английский и китайский языки с моделями `base`, `small` и `large-v3-turbo-q5_0`. Дополнительная модель устанавливается командой `opencode-orchestra voice-model large-v3-turbo-q5_0` (около 547 МиБ, с проверкой SHA-256); вместо неё можно указать `small`. Модель и язык речи выбираются в настройках оверлея или веб-микрофона. `auto` определяет язык каждой записи; для коротких записей или речи на нескольких языках лучше проверить результат и при необходимости выбрать язык явно.

Распознавание идёт через один долгоживущий процесс `whisper-server` (модель остаётся в памяти между диктовками), использует `-t` с числом физических ядер (`ORCHESTRA_VOICE_THREADS` переопределяет), обрезает паузы и на путях оверлея и `voice-tui` распознаёт завершённые 30-секундные сегменты во время речи; браузерный микрофон по-прежнему отправляет запись целиком. На Windows команда `opencode-orchestra voice-accelerator cuda` (или `cuda11`) ставит закреплённую CUDA-сборку; Vulkan собирается локально (`scripts/build-whisper-vulkan.ps1`/`.sh`) и включается командой `voice-accelerator vulkan`. Подробности: [voice-overlay/README.md](voice-overlay/README.md#скорость-распознавания).

Для внешнего TUI-редактора задайте `ORCHESTRA_VOICE_MODEL=base|small|large-v3-turbo-q5_0` и `ORCHESTRA_VOICE_LANGUAGE=ru|en|zh|auto`, выбирая одно значение для каждой переменной. По умолчанию используются `base` и `ru`; оверлей и веб-микрофон сохраняют собственные настройки.

**OpenCode 2 на Windows и Linux — единый хоткей для TUI, Desktop и браузера:**

```powershell
bunx @oeronteros-1/opencode-orchestra@latest voice-overlay
```

Поставьте курсор в поле ввода OpenCode. **Ctrl+Alt+Space** начинает запись; повторное нажатие останавливает её и вставляет распознанный текст через буфер обмена. Отправку нажимаете сами. Серверный порт и прокси для хоткея не нужны. Оверлей должен оставаться запущенным. Во время записи и распознавания сохраняйте исходное окно, вкладку и поле ввода. Если окно, его заголовок или системный фокус изменились, текст остаётся в оверлее и буфере: вернитесь в исходное поле и нажмите тот же хоткей для повторной вставки. Невставленный результат сохраняется после перезапуска оверлея.

Для TUI в старых версиях **OpenCode 1.x** запустите `bunx @oeronteros-1/opencode-orchestra@latest voice-tui`. Нажмите **Ctrl+X, затем E** или `/editor`, наговорите текст и нажмите тот же бинд ещё раз (либо Enter). OpenCode вернёт его в черновик именно этой сессии без отправки. `Ctrl+C` отменяет запись, сохраняя черновик. Команда на время запуска задаёт `EDITOR` и `VISUAL` для голосового ввода; отдельное окно и фиксированный порт не нужны. Для обычного текстового редактора запускайте `opencode` без `voice-tui`.

Окно можно свернуть кнопкой «−» даже во время записи; хоткей остаётся зарегистрирован. Тумблер «Автовставка в поле сессии» включён по умолчанию. При выключении результат остаётся в превью и буфере; после проверки вернитесь в исходное поле и нажмите хоткей для вставки. Linux X11 требует `xclip` (`sudo apt install xclip`), EWMH и XTEST; терминалы используют Ctrl+Shift+V. В исходниках добавлена поддержка Wayland: расширение GNOME, порталы Plasma с kdotool, wl-clipboard/wtype и IPC для Sway/Hyprland. Нужны новая Linux-сборка и [настройка рабочего окружения](voice-overlay/linux/README.md); изменения ещё не опубликованы. При отклонении назначения Wayland текст остаётся в оверлее.

Микрофон внешнего редактора можно выбрать через `ORCHESTRA_VOICE_DEVICE`. В окне эти параметры выбираются в настройках. По умолчанию используются `base`, русский язык и системный микрофон. Для режима совместимости со старым TUI выберите в настройках окна режим «Совместимость с TUI 1.x через сервер»:

```bash
opencode --port 4096
# в другом терминале:
bunx @oeronteros-1/opencode-orchestra@latest voice-overlay
```

Команда запускает отдельное окно на Windows/Linux без добавления его каталога в PATH. Если окно ещё не установлено, CLI устанавливает его из платформенного пакета и подготавливает модель `base`.

Для OpenCode Web запустите в разных терминалах:

```bash
opencode web --port 4096
bunx @oeronteros-1/opencode-orchestra@latest web
```

Откройте `http://127.0.0.1:4097`. Кнопка микрофона появится рядом с отправкой промпта и по умолчанию вставит распознанный текст в черновик. В настройках можно явно выбрать «Вставить и отправить». Если сессия изменилась во время записи или распознавания, результат остаётся в редактируемой панели восстановления; восстановление никогда не отправляет его автоматически.
`web` и `voice-web` — подкоманды CLI `opencode-orchestra`, а не отдельные команды терминала.

В **WSL** команда `voice-overlay` использует Windows-оверлей: кнопка привязывается к окну Windows Terminal или Desktop/WSLg, показывает красную пульсацию и таймер записи. Для текущей локальной сборки из WSL выполните `bash scripts/voice-wsl-overlay.sh` в этом репозитории. Настройки запуска и пути Windows-моделей: [инструкция WSL](voice-overlay/linux/README.md#wsl-кнопка-поверх-терминала-windows--wslg).

Требования платформ и диагностика описаны в [voice-overlay/README.md](voice-overlay/README.md).

## Конфигурация

Глобальный файл:

```text
~/.config/opencode/orchestra.jsonc
```

Файл проекта:

```text
<project>/.opencode/orchestra.jsonc
```

Проектные значения перекрывают глобальные, а явные plugin options перекрывают оба уровня. Поддерживаются `OPENCODE_CONFIG_DIR` и `--config-dir`.

Практический начальный конфиг:

```jsonc
{
  "$schema": "https://unpkg.com/@oeronteros-1/opencode-orchestra@latest/schema/opencode-orchestra.schema.json",
  "budget": "balanced",
  "models": {
    "strategy": "auto",
    "agents": {},
    "fallback": { "enabled": true, "maxRetries": 2, "agents": {} }
  },
  "browser": { "mode": "auto", "profile": "default", "profiles": ["default"] },
  "orchestration": {
    "parallelWorkers": 8,
    "maxWorkers": 8,
    "maxDelegationDepth": 2,
    "parallelEditors": 0,
    "exposeWorkers": false
  },
  "permissions": { "autoAcceptAll": false },
  "telemetry": {
    "enabled": true,
    "directory": ".orchestra",
    "storeTexts": false
  },
  "pricing": {
    "estimate": true,
    "warnThresholdUSD": 0.5,
    "openrouter": { "enabled": false, "ttlHours": 12 }
  }
}
```

Полный контракт и границы значений находятся в [schema/opencode-orchestra.schema.json](schema/opencode-orchestra.schema.json). Расширенный пример: [examples/.opencode/orchestra.jsonc](examples/.opencode/orchestra.jsonc).

`permissions.autoAcceptAll` автоматически подтверждает все запросы разрешений OpenCode. По умолчанию параметр выключен; включайте его только в доверенном workspace.

## Стоимость и телеметрия

Порядок определения цены:

1. явная цена в кандидате модели;
2. цена, сообщённая провайдером;
3. встроенный snapshot или настроенный приватный endpoint;
4. опциональный fallback к публичному каталогу OpenRouter.

Неизвестная цена остаётся неизвестной и никогда не считается бесплатной. Subscription-модели учитываются отдельно от free и paid.

Локальный ledger сохраняет токены, стоимость, идентификаторы моделей и агентов, агрегаты успешности и задержки MCP, решения маршрутизации и очищенные reliability events. Аргументы и сырой вывод MCP не сохраняются. Хранение текстов запросов и ответов включается отдельно.

## Безопасность и приватность

- Dashboard и voice-сервисы по умолчанию доступны только через loopback.
- URL dashboard содержит случайный токен доступа.
- Телеметрия по умолчанию хранится локально в `.orchestra`.
- Текст сообщений не сохраняется без `telemetry.storeTexts: true`.
- Reliability events не содержат сырой текст ошибок провайдера.
- Read-only workers не редактируют файлы и не используют незащищённую нативную делегацию.
- Официальный Git MCP ограничен активным репозиторием.
- Опасные Git reset запрещены, а мутации требуют разрешений соответствующего агента.
- При невалидном конфиге Orchestra переходит на безопасные defaults и не перезаписывает проблемный файл.

- Bun 1.2+ для рекомендуемой установки

```bash
npm ci
npm run check
npm run build
npm pack --dry-run
```

Обычный набор тестов самодостаточен; живые браузерные проверки пропускаются без явного включения. Дополнительные интеграционные проверки:

npm run test:mcp-live

`test:mcp-live` запускает внешние MCP и требует установленных инструментов. `test:browser-live` использует временный тестовый профиль и локальный стенд; отсутствие Chrome отмечается как skipped. `test:browser-e2e` запускает регрессионный Playwright-тест репозитория. Для любой браузерной проверки задайте абсолютный путь к Chrome через `ORCHESTRA_TEST_CHROME`; для E2E можно отдельно установить Playwright Chromium командой `npx playwright install chromium`.

## Диагностика

Начните с:

```bash
bunx @oeronteros-1/opencode-orchestra@latest doctor
```

Если локальный MCP настроен, но не запускается:

```bash
bunx @oeronteros-1/opencode-orchestra@latest mcp-smoke --directory .
```

`--json` включает машиночитаемый результат. На Windows Orchestra находит `.exe`, `.cmd` и `.bat` shims и использует безопасный fallback через `cmd.exe` только там, где это необходимо.
